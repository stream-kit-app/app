# PocketBase (site + app)

Ops notes for the shared PocketBase backend used by `@stream-kit/site` and the desktop app account/cloud features. Schema/layout details also live in `.cursor/rules/pocketbase.mdc` and [Site](./site.mdx).

## Superuser (Docker)

The image runs `pocketbase superuser upsert` on every start when `PB_ADMIN_EMAIL` and `PB_ADMIN_PASSWORD` are set (in `site/pb/.env` or the host environment). It creates the superuser or resets its password to the configured value, so changing the password in the PocketBase dashboard is overwritten on the next restart. Leave both empty to skip.

## Auth rate limits

In production PocketBase admin (`Settings` → **Rate limits** / collection auth options), **enable rate limits** for:

- Auth collection **login** (`authWithPassword`)
- Auth collection **register** (create)
- Related auth endpoints (password reset, email change, verification) as appropriate

Without rate limits, credential stuffing and account spam are trivial. Local/dev instances may leave limits loose; production should restrict by IP (and optionally by identity) for auth routes.

## Collections used by the desktop app

| Collection | Notes |
| --- | --- |
| `users` | Auth; avatar/name/email |
| `subscriptions` / `user_subscriptions` | Plan catalog + membership (`status`, optional `endsAt` grace) |
| `user_files` | Protected media uploads; clients use `pb.files.getToken()` |
| `user_actions` / `user_action_queues` | Config sync; monotone `revision` + LWW |
| `user_plugin_records` | Generic per-record plugin data sync (`pluginKey` + `collection` + JSON `payload`); entitlement via `user_config_sync.pb.js` |
| `user_overlay_projects` | Full overlay authoring sync (metadata + protected `source` zip + `sourceHash`); distinct from public `user_overlays` publish |
| `user_dashboard_widgets` | Dashboard widget layout sync |
| `user_overlays` | Published overlay browser sources: `overlayId` = local overlay id (UUID or short slug, unique, max 64), PB `id` is auto 15-char, `bundle` (zip of `dist/`, public, max 100MB), `config` JSON, `published`. Public list/view when `published = true`; owner CRUD + entitlement hook (`user_overlays.pb.js`). Served by the site at `/app/overlays/[uuid]/`, not as PocketBase UI routes. |

| `ai_usage` | Per-user per-day AI action generator usage (`day` = `YYYY-MM-DD`, `count`, token totals). Written only by `ai_actions.pb.js`; owner can list/view |

## AI actions route

`POST /api/ai/generate-action` (`pb_hooks/ai_actions.pb.js`, prompt and schema in `pb_hooks/shared/ai-actions.js`) turns a description into a draft action via the Anthropic API. It requires auth and an entitled membership, and allows `DAILY_LIMIT` calls per user per day.

| Env var | Notes |
| --- | --- |
| `ANTHROPIC_API_KEY` | Required; without it the route returns 500 |
| `AI_MODEL` | Optional, defaults to `claude-opus-5-5` |
| `ANTHROPIC_WORKSPACE_ID` | Only for API keys that are not scoped to a workspace; sent as `anthropic-workspace-id` |

Local dev: put them in `site/pb/.env` (gitignored); `run-pocketbase.mjs` loads that file before starting PocketBase. Restart PocketBase after changing it. With Docker Compose, the same file feeds the `${...}` substitutions in `docker-compose.yml`.

The client only sends `prompt`, `catalog` (the installed triggers/handlers), and on a repair round `previousAttempt` + `errors`. Model, system prompt and output schema are fixed server-side.

Prefer `pb.filter('user={:id}', { id })` on the JS SDK when building filters with dynamic values.
