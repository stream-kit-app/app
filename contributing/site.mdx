# Site

The `@stream-kit/site` package is the public marketing website for Stream Kit. It lives at the repository root in `site/` and is part of the pnpm workspace.

Documentation is hosted separately — see [Documentation site](#documentation-site-docs-site) below.

## Homepage

The homepage (`site/src/routes/(marketing)/+page.svelte`) is a landing page that positions Stream Kit as the modern alternative to Streamer.bot. It uses the shared **blueprint** visual language (Cloudflare-style rails, hairline rules, crosshairs, collapsed-border grids) from `@stream-kit/ui/blueprint`.

Sections:

- **Hero** — mono eyebrow, headline, download CTA, and the app mock framed in a `Panel` with corner crosshairs on a `blueprint-grid` background
- **Features** — eight capabilities in a 4×2 `CellGrid` with mono indices
- **Plugin showcase** — schematic plugin matrix linking to `/plugins`
- **How it works** — four steps on a dashed connector rail
- **FAQ** — hairline-divided `<details>` list (`+` / `×` toggle)
- **CTA** — hatched band with a crosshaired `Panel`

The marketing layout (`(marketing)/+layout.svelte`) wraps every marketing page in a single `GridFrame` (vertical rails + hatched gutters), sticky header with crosshairs, and a shared footer. `/app/*` stays chrome-free.

The app screenshot in the hero is a dummy built in HTML/CSS (`site/src/routes/(marketing)/app-mock.svelte`) that mimics the app UI (sidebar plus the Bot timers page). Replace it with a real screenshot when available.

The page reuses `@stream-kit/ui` components (`Button`, `Badge`, `Container`, `Logo`) plus blueprint primitives (`GridFrame`, `SectionRule`, `CellGrid`, `Panel`, `Eyebrow`, `Crosshair`) and the shared color tokens from `site/src/routes/layout.css` (including `--color-rule` / `--font-mono`). Content is currently English only; copy lives in plain arrays/constants at the top of `+page.svelte` so it can be extracted for i18n later.

## Plugins page

The plugins catalog lives at `/plugins` (`site/src/routes/(marketing)/plugins/`). It lists official plugin releases from PocketBase and is linked from the site header. The marketplace UI uses the same blueprint primitives as the homepage (`Panel`, hairline dividers, mono labels, sharp frames).

- **Data source** — server-side `PluginsService.listLatest()` queries `plugin_versions` where `isLatest = true`, expands related `plugins` and `files` records, and maps the result to flat catalog entries with a PocketBase file download URL.
- **UI** — rail-aligned filter sidebar + collapsed-border plugin card grid with icon, name, version, description, Stream Kit version requirement, and a download button when a release file is linked.
- **Empty state** — shown when no published plugins exist yet.
- **Error banner** — shown when PocketBase is unreachable (e.g. dev server running without PocketBase).

Plugin records can be seeded from the repo manifests with:

```sh
POCKETBASE_ADMIN_EMAIL=you@example.com POCKETBASE_ADMIN_PASSWORD=your-password pnpm --filter @stream-kit/site pb:seed
```

The script reads `plugins/*/manifest.json`, downloads release zips from GitHub distribution repos, uploads them to the `files` collection, upserts `plugins` + `plugin_versions` records, and marks each manifest version as `isLatest`. PocketBase must be running (`pnpm dev:site` or `pb:serve`). Superuser credentials come from the PocketBase admin UI at [http://127.0.0.1:8090/_/](http://127.0.0.1:8090/_/).

### Manifest API (desktop app)

Official plugins expose a remote manifest for in-app updates at:

```
GET /api/plugins/{key}/manifest.json
```

Example: `https://stream-kit.app/api/plugins/twitch/manifest.json`

The response matches the app's remote manifest shape. `downloadUrl` and `sha256` are derived from the linked `files` record (not stored on `plugin_versions`).

You can also create records manually in the admin UI: upload a zip to `files`, then link it from `plugin_versions`.

## PocketBase

The site uses [PocketBase](https://pocketbase.io/) as its backend. The PocketBase project lives in `site/pb/`:

| Path | Purpose |
| --- | --- |
| `site/pb/pocketbase` (or `.exe` on Windows) | Downloaded executable (gitignored) |
| `site/pb/pb_data/` | Local database and uploads (gitignored) |
| `site/pb/pb_migrations/` | Collection migrations (`plugins`, `plugin_versions`, `files`, `plugin_reviews`, `subscriptions`, …) |
| `site/pb/pb_hooks/` | JavaScript hooks (including `files.pb.js` metadata sync) |
| `site/pb/PB_VERSION` | PocketBase binary version (local setup + Docker) |
| `site/pb/package.json` | `@stream-kit/pocketbase` package (changeset version + GHCR image tags) |
| `site/pb/Dockerfile` | Production image with binary, hooks, and migrations |
| `site/pb/docker-compose.yml` | Example stack for Dockhand (`pb_data` volume) |
| `site/src/lib/pocketbase/types.ts` | Generated PocketBase TypeScript types |

On first run, the PocketBase binary downloads automatically. The admin UI is at [http://127.0.0.1:8090/_/](http://127.0.0.1:8090/_/).

Root `pnpm dev` starts PocketBase as its own Turbo task (`@stream-kit/pocketbase#dev`). On boot it:

1. Ensures `packages/app/.env` and `site/.env` exist (`pnpm bootstrap`)
2. Upserts a local superuser (`POCKETBASE_ADMIN_EMAIL` / `POCKETBASE_ADMIN_PASSWORD`, defaults `admin@stream-kit.local` / `stream-kit-dev` — **local-only**; never point `PUBLIC_POCKETBASE_URL` at a remote host while running this task)
3. Seeds local data when healthy (localhost only):
   - default / `SK_DEV_SEED=full` — create `pro` plan if missing + grant active memberships to users without entitlement
   - `SK_DEV_SEED=plan` — create `pro` plan if missing (no membership writes)
   - `SK_DEV_SEED=0` — skip seeding

If PocketBase is already listening on the target port, the task **exits with an error** so Turbo owns a single local process (stop the other instance first).

### Hook handler scope

PocketBase serializes every hook handler and runs it in an isolated JS runtime, so a handler **cannot** see functions or constants declared at the top level of its `*.pb.js` file (`ReferenceError: x is not defined`). Shared helpers live in `site/pb/pb_hooks/shared/*.js` and must be loaded inside the handler body:

```js
function requireActiveSubscription(e) {
	const entitlement = require(`${__hooks}/shared/entitlement.js`);
	// …
	return e.next();
}
```

`shared/` is part of the production image; `lib/` (schema codegen) is not.

### Production Docker image

The production image is published to GitHub Container Registry as `ghcr.io/stream-kit-app/pocketbase`. It includes the PocketBase binary (version from `PB_VERSION`), production `pb_hooks/` (e.g. `files.pb.js`, `user_files.pb.js`, …), and `pb_migrations/`. Local-only schema codegen (`main.pb.js`, `handler.js`, `config.json`, `lib/`, `views/`) is excluded via `.dockerignore`. Runtime data (`pb_data`) must be a persistent volume — never bake it into the image.

Versioning:

1. Change hooks, migrations, `Dockerfile`, or `PB_VERSION`.
2. Run `pnpm changeset` and select `@stream-kit/pocketbase` (`@stream-kit/site` stays ignored by changesets).
3. Merge the version PR on `main`. The Release workflow triggers `publish-pocketbase.yml`, which pushes tags `VERSION`, `vVERSION`, and `latest`. If that version tag already exists on GHCR, the publish job is a no-op.

Example Compose / Dockhand stack (also in `site/pb/docker-compose.yml`):

```yaml
services:
  pocketbase:
    image: ghcr.io/stream-kit-app/pocketbase:latest
    ports:
      - '8090:8090'
    volumes:
      - pb_data:/pb/pb_data
    restart: unless-stopped

volumes:
  pb_data:
```

In Dockhand, register GHCR (`https://ghcr.io`) with a GitHub PAT that has `read:packages` when the package is private. Point the Cloudflare Tunnel at the service on port `8090`. On first start, create a superuser from the installer URL in the logs or with `pocketbase superuser create`.

Manual publish: Actions → **Publish PocketBase** → Run workflow (optional force rebuild).

### Collections

**`plugins`** — stable plugin identity:

| Field | Description |
| --- | --- |
| `name` | Display name (unique) |
| `key` | Plugin identifier (unique, e.g. `twitch`) |
| `description` | Short catalog description |
| `icon` | Iconify icon id (e.g. `ri:twitch-fill`) |
| `author` | Relation to auth users |

Both `plugins`, `plugin_versions`, and `files` have public read rules (`listRule` / `viewRule` = `""`) so the catalog and release downloads can be fetched without admin credentials. Write access remains admin-only.

**`files`** — uploaded release zips with hook-populated metadata:

| Field | Description |
| --- | --- |
| `file` | Zip upload (max 50 MB) |
| `mimeType` | Set automatically by `files.pb.js` |
| `size` | File size in bytes (hook) |
| `sha256` | SHA-256 hex digest (hook) |
| `originalName` | Original upload filename (hook) |

**`plugin_versions`** — release-specific manifest data, linked to a plugin:

| Field | Description |
| --- | --- |
| `plugin` | Relation to `plugins` (cascade delete) |
| `file` | Relation to `files` (release zip) |
| `version` | Semver string |
| `streamKitVersion` | Supported app version range |
| `entry` | Plugin entry file (e.g. `dist/index.js`) |
| `changelog` | Release notes |
| `isLatest` | Marks the current release |
| `publishedAt` | Publication date |

Unique index on `(plugin, version)`.

**`subscriptions`** — admin catalog of plans that unlock cloud app features:

| Field | Description |
| --- | --- |
| `key` | Stable identifier (unique, e.g. `pro`) |
| `name` | Display name |
| `description` | Short catalog description |
| `icon` | Iconify icon id |
| `enabled` | When `true`, visible via public list/view rules |
| `bullets` | JSON array of benefit strings for plan cards (e.g. `["Cloud sync", "Priority support"]`) |
| `maxFileBytes` | Max size per `user_files` upload (bytes) |
| `maxStorageBytes` | Total `user_files` storage quota per user on this plan (bytes) |

Public `listRule` / `viewRule` is `enabled = true`. Create/update/delete are admin-only (`null` rules).

**`user_subscriptions`** — membership lifecycle history (multiple rows over time):

| Field | Description |
| --- | --- |
| `user` | Relation to `users` |
| `subscription` | Relation to `subscriptions` (the plan for that period) |
| `purchasedAt` | When this membership started |
| `cancelledAt` | When cancelled (optional) |
| `status` | `active`, `cancelled`, or `expired` |

Users may list/view their own rows. Create/delete remain admin-only until purchase flows exist. Owners may **cancel** an active membership (`status` → `cancelled`, optional `cancelledAt`). The app resolves the current plan by querying the latest `user_subscriptions` row with `status = "active"` (expand `subscription`).

**`user_files`** — authenticated user media (audio/images/video for actions and rankings icons):

| Field | Description |
| --- | --- |
| `user` | Relation to `users` (owner) |
| `file` | Uploaded blob |
| `mimeType` / `size` / `originalName` | Filled by `user_files.pb.js` on create |

Owner-only list/view/create/delete. Create hook rejects uploads without an active plan or when over `maxFileBytes` / `maxStorageBytes`. Marketplace release zips remain in the separate **`files`** collection.

### Type generation

During `dev`, nodemon watches `site/pb/pb_migrations/` and regenerates `site/src/lib/pocketbase/types.ts` via [`pocketbase-typegen`](https://github.com/patmood/pocketbase-typegen) whenever a migration file changes.

Types are read from the local SQLite database (`pb_data/data.db`), so PocketBase must be running and must have applied the latest migrations before the generated types match your schema edits. Restart PocketBase after changing migrations, then save a migration file again (or run `pb:typegen` manually) to refresh types.

Useful package scripts:

```sh
pnpm --filter @stream-kit/site pb:setup        # download PocketBase only
pnpm --filter @stream-kit/site pb:serve        # run PocketBase only
pnpm --filter @stream-kit/pocketbase dev       # same as pb:serve (Turbo entry)
pnpm --filter @stream-kit/site pb:typegen      # generate types once
pnpm --filter @stream-kit/site pb:typegen:watch # watch migrations and regenerate types
pnpm --filter @stream-kit/site pb:seed           # seed plugins from repo manifests
pnpm --filter @stream-kit/site dev:site          # run the SvelteKit dev server only
```

## Development

From the repository root:

```sh
pnpm dev        # packages + plugins + PocketBase + site + Tauri (docs opt-in)
pnpm dev:site   # PocketBase + site only
pnpm dev:all    # same as `pnpm dev`, plus docs site
pnpm bootstrap  # create missing .env files from .env.example
```

`pnpm --filter @stream-kit/site dev` starts typegen watch + Vite (PocketBase is a separate Turbo package). The Vite dev server attaches an in-memory overlay WebSocket hub at `/ws?overlayId=` (used by cloud browser sources).

Or run commands directly in the package:

```sh
pnpm --filter @stream-kit/site dev       # typegen + Vite (local /ws via Node hub)
pnpm --filter @stream-kit/site build     # Worker bundle + Durable Object exports
pnpm --filter @stream-kit/site preview   # wrangler dev (SSR + Durable Object /ws)
pnpm --filter @stream-kit/site deploy    # wrangler deploy to Cloudflare Workers
```

### Cloud overlays (`/app/overlays/[uuid]`)

Published overlay bundles live in PocketBase (`user_overlays`) and are served by the site (not PocketBase UI routes):

| Path | Role |
| --- | --- |
| `/app/overlays/[uuid]/` | Browser source HTML + assets from the published `dist` zip |
| `/ws?overlayId=[uuid]` | Live events; OBS connects as subscriber; desktop app as `role=publisher` with PB auth token |

In production, `/ws` is routed to a **Durable Object** (`OverlayRoom`, one instance per `overlayId`) with hibernatable WebSockets. Local `vite dev` still attaches the in-memory Node hub via `overlay-ws/vite-plugin.mjs` so overlays work without Wrangler.

Marketing routes live under `site/src/routes/(marketing)/` so `/app/*` stays free of marketing chrome (future logged-in dashboard shell).

## Stack

- SvelteKit with `@sveltejs/adapter-cloudflare` (Workers + static assets)
- Overlay WebSockets via Cloudflare Durable Objects (`OVERLAY_ROOMS` → `OverlayRoom`)
- Svelte 5 (runes mode)
- Tailwind CSS v4
- `@stream-kit/ui` + `@stream-kit/ui/blueprint` (rails, rules, crosshairs, cell grids, panels)
- Shared blueprint utilities in `packages/ui/src/styles/blueprint.css` (imported by site and app `layout.css`)

## Deployment (marketing site)

GitHub Actions workflow `.github/workflows/deploy-site.yml` builds with `pnpm build:site` and deploys the Worker from `site/` via `cloudflare/wrangler-action` (`wrangler deploy`).

Worker name: `stream-kit-site` (see `site/wrangler.jsonc`). Custom domain: `stream-kit.app` (attach in the Cloudflare dashboard after the first deploy).

Required repository secrets (shared with docs deploy):

- `CLOUDFLARE_API_TOKEN` — API token with **Workers Scripts: Edit** (and Durable Objects) in addition to Pages if you reuse the docs token
- `CLOUDFLARE_ACCOUNT_ID`

```sh
gh secret set CLOUDFLARE_API_TOKEN
gh secret set CLOUDFLARE_ACCOUNT_ID
```

Build-time env for the catalog:

- `PUBLIC_POCKETBASE_URL` — production default `https://api.stream-kit.app` (also set as a Worker `vars` entry for Durable Object auth)

## Documentation site (`docs-site/`)

User-facing documentation is published at [https://docs.stream-kit.app](https://docs.stream-kit.app).

| Item | Location |
| --- | --- |
| Package | `@stream-kit/docs` in `docs-site/` |
| Framework | Next.js + Fumadocs MDX |
| Content | `/docs` (`.mdx` files + `meta.json` sidebars) |
| Deploy | Cloudflare Pages (static export to `docs-site/out/`) |

### Content workflow

- Write docs in `/docs` as `.mdx` with YAML frontmatter (`title`, optional `description`).
- Sidebar order is controlled by `meta.json` in `/docs` and each section folder (`get-started/`, `guide/`, `plugins/`, `api/`, `developers/`).
- Internal links use Fumadocs paths such as `/docs/guide/actions` (not `.md` relative paths).
- Run `pnpm generate:docs-reference` before `pnpm build:docs` to refresh API reference pages from plugin definitions.

### Development

From the repository root:

```sh
pnpm dev:docs   # docs only
pnpm dev:all    # full stack including docs
```

Or directly in the package:

```sh
pnpm --filter @stream-kit/docs dev
pnpm --filter @stream-kit/docs build
pnpm --filter @stream-kit/docs preview
```

### Deployment

GitHub Actions workflow `.github/workflows/deploy-docs.yml` builds with `pnpm build:docs` and deploys from `docs-site/` via `cloudflare/wrangler-action` (`pages deploy out`, `workingDirectory: docs-site`). Wrangler is a `devDependency` of `@stream-kit/docs` so the action does not need to install it on the workspace root.

Local deploy: `pnpm --filter @stream-kit/docs deploy`.

Required repository secrets:

- `CLOUDFLARE_API_TOKEN` — API token with **Cloudflare Pages: Edit** (docs) and **Workers Scripts: Edit** (marketing site) when shared
- `CLOUDFLARE_ACCOUNT_ID`

```sh
gh secret set CLOUDFLARE_API_TOKEN
gh secret set CLOUDFLARE_ACCOUNT_ID
```

Cloudflare Pages project name: `stream-kit-docs`. Custom domain: `docs.stream-kit.app`.
The marketing site header links to the docs site externally (`https://docs.stream-kit.app`).
