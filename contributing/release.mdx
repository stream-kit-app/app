# Release pipeline

Stream Kit uses [Changesets](https://github.com/changesets/changesets) for versioning and GitHub Actions for building and publishing releases. The app is currently on the **alpha** pre-release channel (`0.1.0-alpha.x`).

## Overview

```text
PR with changeset → merge to main → Version Packages PR → merge → git tag (v*) → CI build → GitHub Release
                                                                                              ↓
                                                                                    Microsoft Store (optional)
                                                                                              ↓
                                                                              npm (@stream-kit/plugin, @stream-kit/core)
                                                                                              ↓
                                                                              plugin distribution zips (Publish Plugins)
```

| Workflow                                                                        | Trigger                          | Purpose                                                                                               |
| ------------------------------------------------------------------------------- | -------------------------------- | ----------------------------------------------------------------------------------------------------- |
| [`.github/workflows/release.yml`](../.github/workflows/release.yml)             | Push to `main`                   | Opens or updates a **Version Packages** PR; on merge, creates a `v*` git tag and dispatches the build |
| [`.github/workflows/build-release.yml`](../.github/workflows/build-release.yml) | Push tag `v*` or manual dispatch | Builds Windows installers and optionally publishes an MSIX bundle to the Microsoft Store              |
| [`.github/workflows/publish-npm.yml`](../.github/workflows/publish-npm.yml)       | Push tag `v*`                    | Publishes `@stream-kit/plugin` and `@stream-kit/core` to the public npm registry                      |
| [`.github/workflows/publish-plugins.yml`](../.github/workflows/publish-plugins.yml) | Push tag `v*` or manual dispatch | Publishes first-party plugin distribution zips to GitHub distribution repos                           |

## Adding a changeset

When your PR includes a user-facing change, add a changeset:

```bash
pnpm changeset
```

### Desktop app (`@stream-kit/app`)

1. Select **@stream-kit/app** only.
2. Choose the bump type: `patch`, `minor`, or `major`.
3. Write a short summary for the changelog.
4. Commit the generated `.changeset/*.md` file with your PR.

Packages like `@stream-kit/site` are ignored. Workspace deps are not versioned unless you add a changeset for them.

### Plugin SDK (`@stream-kit/plugin` + `@stream-kit/core`)

When you change the public plugin API or shared runtime helpers in [`packages/plugin/`](../packages/plugin/) or [`packages/core/`](../packages/core/):

1. Run `pnpm changeset` and select **both** `@stream-kit/plugin` and `@stream-kit/core` (they are **linked** in [`.changeset/config.json`](../.changeset/config.json) and always share the same version).
2. Choose the bump type and write a summary for plugin authors.
3. Commit the changeset with your PR.

After the Version Packages PR merges, CI publishes both packages to npm when the `v*` tag is pushed.

## Release flow

1. Merge a PR that contains one or more changesets into `main`.
2. The **Release** workflow opens a **Version Packages** PR (or updates an existing one).
3. Review the version bump and changelog, then merge the Version Packages PR.
4. The Release workflow pushes a tag like `v0.1.0-alpha.1` to GitHub.
5. The Release workflow explicitly dispatches **Build Release** for that tag.

Publish the draft release on GitHub when you are ready to ship.

### Build did not start?

**Build Release** runs when a `v*` tag is pushed or when `Release` dispatches it manually. GitHub does not reliably start a second workflow from a tag pushed with the default `GITHUB_TOKEN`, so `Release` also calls `gh workflow run build-release.yml`.

The release workflow requires `actions: write`, `contents: write`, and `pull-requests: write` permissions. If GitHub blocks PR creation, configure `CHANGESET_GITHUB_TOKEN` as described below.

To build an existing tag manually:

1. Go to **Actions → Build Release → Run workflow**
2. Enter the tag (e.g. `v0.1.0-alpha.1`) and run

Or re-push the tag from your machine:

```bash
git push origin refs/tags/v0.1.0-alpha.1 --force
```

## Alpha channel

The repo is in Changesets pre-release mode with tag `alpha` (see [`.changeset/pre.json`](../.changeset/pre.json)). Version bumps produce prerelease versions such as `0.1.0-alpha.1`.

To leave the alpha channel and publish stable releases:

```bash
pnpm changeset pre exit
pnpm version-packages
```

Commit the result, then continue with the normal release flow.

## Version sync

[`packages/app/package.json`](../packages/app/package.json) is versioned independently by Changesets. [`@stream-kit/plugin`](../packages/plugin/package.json) and [`@stream-kit/core`](../packages/core/package.json) share a linked version.

After each `changeset version`, [`scripts/sync-app-version.mjs`](../scripts/sync-app-version.mjs) copies the app version to:

- [`packages/app/src-tauri/tauri.conf.json`](../packages/app/src-tauri/tauri.conf.json)
- [`packages/app/src-tauri/Cargo.toml`](../packages/app/src-tauri/Cargo.toml)
- [`packages/app/src-tauri/tauri.windows.conf.json`](../packages/app/src-tauri/tauri.windows.conf.json) — sets `bundle.windows.wix.version` to a numeric-only MSI version (e.g. `0.1.0-alpha.3` → `0.1.0.3`). WiX does not accept semver pre-release labels like `alpha`.

## Local builds

Build Windows installers:

```bash
pnpm build
pnpm tauri build
```

Build a Microsoft Store MSIX bundle:

```bash
pnpm build
pnpm --filter @stream-kit/app tauri:windows:build -- --arch x64 --runner pnpm
```

Output:

- Tauri installers: `packages/app/src-tauri/target/release/bundle/`
- MSIX bundle: `packages/app/src-tauri/target/msix/*.msixbundle` (only when Store publishing is enabled)

## npm publish (plugin SDK)

`@stream-kit/plugin` and `@stream-kit/core` are published to the **public** npm registry under the `@stream-kit` scope. They ship with an MIT license (see `packages/plugin/LICENSE` and `packages/core/LICENSE`), separate from the source-available license on the main app repository.

### Manual publish

```bash
pnpm build:packages
pnpm publish:npm
```

Requires `NPM_TOKEN` in the environment and publish access to the `@stream-kit` scope.

### Plugin starter template

The public GitHub template for external plugin authors lives at [stream-kit-app/plugin-starter](https://github.com/stream-kit-app/plugin-starter). The monorepo keeps [`packages/plugin-template/`](../packages/plugin-template/) for internal development.

After changing the template, sync to GitHub:

```bash
pnpm sync:plugin-starter
```

Create the repository once (if it does not exist yet):

```bash
pnpm create:plugin-starter-repo
```

Then enable **Template repository** in the GitHub repo settings for the **Use this template** button.

## GitHub secrets

### Automatic

| Secret                   | Purpose                                                                                          |
| ------------------------ | ------------------------------------------------------------------------------------------------ |
| `GITHUB_TOKEN`           | Provided by GitHub Actions for releases and changesets                                           |
| `CHANGESET_GITHUB_TOKEN` | Optional PAT for creating Changesets PRs and pushing tags when org settings block `GITHUB_TOKEN` |
| `NPM_TOKEN`              | npm automation token with publish access to `@stream-kit/plugin` and `@stream-kit/core`          |
| `PLUGIN_PUBLISH_TOKEN`   | PAT with `repo` scope to push manifests and releases to `stream-kit-app/plugin-*` distribution repos (required for **Publish Plugins** CI; `GITHUB_TOKEN` cannot write to other repositories) |

### Plugin distribution repos (required for Publish Plugins CI)

The **Publish Plugins** workflow pushes `manifest.json` updates and release zips to `stream-kit-app/plugin-{bot,core,obs,...}`. Configure **`PLUGIN_PUBLISH_TOKEN`** as a fine-grained or classic PAT that can write to those repositories in the `stream-kit-app` org.

Without this secret, CI falls back to `GITHUB_TOKEN`, which only has access to the `app` repository and git push / `gh release` steps will fail on the distribution repos.

Configure these in **Settings → Secrets and variables → Actions**:

| Secret                           | Purpose                                 |
| -------------------------------- | --------------------------------------- |
| `AZURE_AD_TENANT_ID`             | Azure AD tenant for Partner Center API  |
| `AZURE_AD_APPLICATION_CLIENT_ID` | App registration client ID              |
| `AZURE_AD_APPLICATION_SECRET`    | App registration client secret          |
| `SELLER_ID`                      | Partner Center seller ID                |
| `MSSTORE_PRODUCT_ID`             | Store product ID after app registration |

Also set repository variable **`MSSTORE_PUBLISH`** to `true` when all Store secrets are configured. Without it, the Store publish job is skipped so CI does not fail before Partner Center is set up.

See [Publish app updates to Microsoft Store with GitHub Actions](https://learn.microsoft.com/en-us/windows/apps/publish/msstore-dev-cli/github-actions) for creating the Azure AD app and obtaining credentials.

### Optional (later)

| Secret                               | Purpose                                                  |
| ------------------------------------ | -------------------------------------------------------- |
| `TAURI_SIGNING_PRIVATE_KEY`          | Tauri updater signing                                    |
| `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` | Updater key password                                     |
| Windows code signing certificate     | Signed NSIS/MSI on GitHub Releases (Store re-signs MSIX) |

## Microsoft Store setup

1. Enroll as a [Microsoft Store developer](https://learn.microsoft.com/en-us/windows/apps/get-started/sign-up).
2. Register the app in [Partner Center](https://partner.microsoft.com/dashboard/apps-and-games/overview) as an MSIX app.
3. Update [`packages/app/src-tauri/gen/windows/bundle.config.json`](../packages/app/src-tauri/gen/windows/bundle.config.json):
    - Set `publisher` to the exact Partner Center publisher CN (replace the `CN=Stream Kit B.V.` placeholder).
    - Ensure `publisherDisplayName` matches Partner Center (`Stream Kit B.V.`).
4. Configure GitHub secrets and set `MSSTORE_PUBLISH=true`.
5. Merge a Version Packages PR; CI builds the MSIX bundle once, uploads it to GitHub Releases, and submits it to Partner Center.

## Build artifacts per platform

| Platform        | Artifacts                         |
| --------------- | --------------------------------- |
| Windows         | `.msi`, `.exe` (NSIS)             |
| Microsoft Store | `.msixbundle` (x64, optional job) |

## Notes

- `bundle.publisher` in Tauri config must not match `productName` (`Stream Kit`); use `Stream Kit B.V.`.
- GitHub Releases are created as **drafts**; publish manually after verifying artifacts.
